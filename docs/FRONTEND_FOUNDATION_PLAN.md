## 1. Expo project setup

**Approach:** Managed workflow with Continuous Native Generation (CNG). `npx create-expo-app` with the TypeScript template, then strip the demo content.

- **Pin the SDK at init.** Do not hand-write a version — let `create-expo-app` resolve the current stable SDK and pin it. All `expo-*` packages are then installed via `npx expo install` so they resolve to the SDK-compatible versions rather than npm `latest`. This single rule prevents the most common class of Expo breakage.
- **No `ios/` or `android/` directories committed.** Native dirs are generated by prebuild. Committing them forfeits CNG and makes SDK upgrades painful. Revisit only if a native module without Expo support becomes unavoidable.
- **Development builds, not Expo Go**, from the point the first native-permission module lands (location, notifications, secure store). Expo Go cannot host custom native config. Budget for this — it is a real setup cost on day one of the maps/notifications work, not later.
- **EAS Build** for distribution. Config file scaffolded now, credentials deferred.
- `app.config.ts` (TypeScript, not `app.json`) so environment values can be computed — see §10.

**Tonight:** scaffold, strip demo, configure. **Deferred:** EAS credentials, dev-build creation, splash/icon assets (FIGMA_PENDING).

## 2. TypeScript configuration

Extend `expo/tsconfig.base`, then tighten. Non-negotiable flags:

| Flag | Why |
|---|---|
| `strict: true` | Baseline. |
| `noUncheckedIndexedAccess: true` | Array/record access yields `T \| undefined`. Directly relevant: cook lists, slot lists, specialty grids are all indexed access over server arrays that may be empty. |
| `exactOptionalPropertyTypes: true` | Distinguishes "absent" from "explicitly undefined" — matters when a backend omits a field vs nulls it. |
| `noImplicitOverride`, `noFallthroughCasesInSwitch` | The booking-state renderer (§18) is a large exhaustive switch; fallthrough there is a real hazard. |
| `verbatimModuleSyntax: true` | Forces `import type`, keeps the bundle honest. |

**Path aliases:** `@/*` → `src/*`, plus per-layer aliases (`@features/*`, `@core/*`, `@ui/*`). Configured in both `tsconfig.json` and the Babel module-resolver so runtime and typecheck agree.

**Typecheck runs in CI as a separate gate from lint and test.** A plan that only lints will let type errors reach main.

## 4. Navigation architecture

**Recommendation: `expo-router`.** Rationale: it is built on React Navigation, so nothing is lost in primitives; file-based routing keeps `src/app/` a readable map of the product; and typed routes plus first-class deep linking matter here specifically — a push notification saying "your cook has arrived" must open *that booking* at *its current state* (§17, §18). Hand-rolling that linking config on bare React Navigation is the main cost avoided.

Proposed group structure:

```
app/
  _layout.tsx                 # providers, session gate, splash hold
  (auth)/                     # unauthenticated stack        DESIGN_PENDING
  (app)/
    _layout.tsx               # FIGMA_PENDING: tabs vs stack — unconfirmed
    home/
    booking/[id]/             # lifecycle host — see §18
    history/
    profile/
    address/
  (modals)/                   # taxes dialog, confirmations
```

**Confirmed by the audit and safe to design against now:**
- Splash holds until session resolves, then routes to Login or Home (audit §R).
- Two bottom sheets exist: Instant duration (`1:728`) and Extension (`3:2002`).
- One modal dialog: taxes popup (`25:1585`) presented over the Instant sheet — i.e. **overlay-over-overlay**, which constrains the sheet library choice (§15).
- Booking lifecycle is a sequence of full screens, not a wizard within one route.

**Settled by the 2026-08-14 product rulings** (`FIGMA_USER_APP_AUDIT.md` § W):
- **No payment routes exist.** `Pay →` opens **Razorpay checkout directly** — there is no Spoon payment or payment-review screen to route to (R-1). After checkout returns — success, failure or dismissal — the client **refetches authoritative booking state** and renders it; it never infers success. Consistent with §18 and §20.
- **Home is one route with booking-state variants** (R-2): `1:455` pre-booking, `59:520` active-booking with the COOK EN-ROUTE card. Not two routes.
- **No Upcoming Bookings route** (R-5): active bookings surface on Home. This lowers the risk on the tab-bar question below — the app is usable without a bookings tab.
- **No separate address-rejection route** (R-4): serviceability is surfaced inline in the map step.

**FIGMA_PENDING — cannot be settled tonight:**
- Whether a bottom tab bar exists at all. Home / History / Profile / Refund history exist as screens, which *suggests* tabs, but no tab bar has been visually confirmed on any of the 12 verified frames. Building tabs now risks a wrong shell.
- Whether Refund history (`71:615`) is a top-level destination or a filtered view of Booking history (`6:227`) — the pending doc flags this as changing navigation.
- Back-navigation policy during a live session (can the user leave In-service?).

**Consequence:** scaffold the router with groups and a **single placeholder shell**; do not commit to tabs until confirmed.

## 5. API client architecture

**Constraint: no backend contract exists. No endpoint, path, verb, payload shape or enum will be written tonight.** What follows is transport mechanism only.

Layers:

1. **`core/api/client.ts`** — a typed `fetch` wrapper. Base URL from config (§10), timeout via `AbortController`, JSON handling, correlation-ID header per request for support triage.
2. **Request interceptors** — inject `Authorization` from the session (§8), attach app version and platform.
3. **Response interceptors** — normalize *every* failure into the error taxonomy (§11) so no raw fetch rejection escapes the layer. Handle 401 → single-flight refresh → retry once → on failure, terminate session.
4. **`core/api/types.ts`** — deliberately **empty** except for envelope-agnostic generics. Backend types land here.

**When the contract arrives:** generate types with `openapi-typescript` rather than hand-writing them, and validate responses at the boundary with `zod`. Adopt zod as the *mechanism* now; write zero schemas until there is a contract to describe. Boundary validation is worth the cost here specifically because the client is a pure consumer of authoritative state — silent contract drift would surface as a mis-rendered booking rather than a crash.

**Single-flight refresh is the one piece of real complexity** and it is design-independent: concurrent 401s must produce one refresh, not N. Buildable and unit-testable tonight against a mock.

## 6. Server-state management

**TanStack Query (React Query).** This is the single most load-bearing choice in the plan, and it follows directly from the responsibility boundary: the backend owns booking state, so nearly everything on screen is a cache of server truth. React Query is purpose-built for exactly that.

Conventions to fix now:

- **Query-key factory** per feature (`bookingKeys.detail(id)`), never inline string arrays. Makes invalidation auditable.
- **Defaults:** conservative `staleTime`, retry disabled for 4xx, enabled for network/5xx.
- **Live booking polling** — the lifecycle screens (En route → Arrived → In service) need fresh server state. Polling interval driven by booking state, with `refetchOnAppFocus`. **The polling cadence per state is a backend-contract question** (or better, push/websocket-driven); the *mechanism* is buildable now.
- **Never derive booking status client-side from a timer.** See §19 and §20.
- Mutations invalidate rather than optimistically rewrite booking state. Optimistic updates are appropriate for cosmetic things (favouriting a cook), never for lifecycle transitions — the client is not entitled to predict a transition it does not own.

## 7. Minimal client-state management

**Zustand**, kept deliberately small. Justification: the only genuinely client-owned state is the **pre-submission booking draft** and ephemeral UI.

| Store | Owns | Notes |
|---|---|---|
| `bookingDraftStore` | User's in-progress selections before submission: instant vs scheduled, chosen day/time/duration | The moment the booking is submitted, ownership transfers to the server and this store is cleared. This boundary is the whole point. |
| `uiStore` | Sheet/modal visibility, transient banners | |
| `sessionStore` | Auth status only (§8) | Tokens live in SecureStore, never here. |

**Explicit non-goals:** no Redux, no global cache of server data, no client-side mirror of booking state. If a piece of state has a server opinion, it belongs in React Query.

## 8. Authentication / session architecture

**FIGMA_PENDING:** the primary auth method is unverified — `53:174` Page 17 Login has not been seen. Phone/OTP vs email vs social is unknown, as is whether a country-code picker exists.
**DESIGN_PENDING:** no OTP screen exists in the file at all. The audit flags this as a probable missing design (question 6 in the export request).

**Buildable tonight — headless session machinery, no screens:**

A session state machine with explicit states: `bootstrapping → unauthenticated | authenticated → refreshing → expired`. Properties that hold regardless of which auth method the design lands on:

- Splash holds until bootstrap resolves (confirmed by audit §R).
- Token refresh is single-flight and shared with the API layer (§5).
- Logout clears SecureStore, resets the QueryClient cache, and resets navigation — **all three**; missing the cache reset leaks the previous user's bookings into the next session.
- 401 after refresh failure terminates the session from anywhere in the app.

**Not buildable:** login/OTP screens, the auth API calls (no contract), resend/timeout rules, error copy.

## 9. Secure token storage

**`expo-secure-store`** — Keychain on iOS, Keystore-backed on Android.

- **Tokens never touch AsyncStorage, Zustand, or React Query.** One module (`core/auth/tokenStore.ts`) is the only code that reads or writes them.
- **Caveat to design around:** SecureStore values have a practical size limit (~2 KB). Large JWTs with fat claims can exceed it. Store the minimum — access token, refresh token, expiry — and never a serialized user profile.
- Interface kept narrow (`get`/`set`/`clear`) so the implementation is swappable and mockable in tests.
- Biometric gating (`requireAuthentication`) is available but **not** proposed until the design says so.

Fully buildable and unit-testable tonight.

## 10. Environment configuration

- `app.config.ts` reads `process.env` and exposes non-secret values via `extra`, read back through `expo-constants`.
- Three environments: `development`, `staging`, `production`, each with its own bundle identifier and app name so all three can coexist on one device.
- **`EXPO_PUBLIC_*` variables are embedded in the JS bundle in plaintext.** They are for API base URLs and feature flags. **No secret, key, or token may ever be one.** Stating this now because it is the single most common leak in Expo apps.
- `core/config/index.ts` parses and validates env at startup and **fails fast** with a clear message rather than letting `undefined` propagate into a fetch URL.
- `.env.example` committed; `.env*` gitignored.

**Blocked:** actual API base URLs — no backend contract or environment list exists. Placeholders, clearly marked.

## 11. Error handling

**Error taxonomy** (`core/errors/`), a discriminated union: `NetworkError | TimeoutError | AuthError | ValidationError | ServerError | UnknownError`. Every error crossing the API boundary is normalized into one of these — feature code never sees a raw fetch rejection.

- **Error boundaries** at three levels: root (catastrophic), per-navigator (screen crash without killing the app), and around the booking-lifecycle host specifically (§18), where an unexpected server state must degrade rather than white-screen.
- **User-facing message mapping** lives in one place, keyed by error type. **FIGMA_PENDING:** all error copy, error-state layouts, and the login error region are unverified. Ship with neutral placeholder strings, clearly marked.
- **Rule for the render layer:** an unrecognised backend state or a missing field renders a safe fallback and logs — it never throws. The client cannot assume it knows every state the backend will send (§18).

## 12. Logging

A thin `core/logging/logger.ts` with levels and pluggable sinks — console in development, no-op in production until a real sink is chosen.

**Redaction is a first-class requirement, not a nicety.** This app handles material that must never reach a log or crash report:

| Never log | Where it appears |
|---|---|
| OTP digits (start and end) | Page 9 Arrived, Page 10 In service |
| Full address, flat/floor/landmark | Address flow, In-service header |
| Phone numbers | Login, Call Cook |
| Auth tokens | API layer |
| Cook personal details | Cook profile cards |

Redaction is implemented as a deny-list transform in the logger itself, so a careless call site cannot leak. Unit-testable tonight.

Crash reporting (Sentry or equivalent) is **deferred** — it is a decision with privacy implications that deserves its own conversation, and the redaction layer must exist first.

## 17. Notifications abstraction

## 18. Booking-state rendering architecture

**This is the section where the responsibility boundary is enforced in code.**

The audit establishes the lifecycle *screen sequence* structurally: Confirmation → En route (on-time / late) → Arrived (+ Start OTP) → In service → Completion, with Cancellation branching off. That sequence is confirmed. **The backend's state names are not** — no contract exists, so no enum will be written.

**Proposed pattern — a state-driven host route:**

```
app/(app)/booking/[id]  →  fetches authoritative booking  →  renders by server state
```

Rules, all of which follow from "the frontend consumes authoritative backend state and renders it":

1. **A single server-provided status field selects the screen.** There is one mapping table, in one file.
2. **The client never computes, infers or advances a state.** Not from a timer, not from an OTP entry, not from a map position. It submits an action and re-reads the result.
3. **Exhaustive switch with a mandatory `default` fallback.** An unrecognised status renders a safe generic state and logs — it does not crash and does not guess. This is essential: the backend will add states, and old app versions must survive them. `noFallthroughCasesInSwitch` (§2) backs this up.
4. **Sub-states are server-driven too.** En-route on-time vs late (`3:1381` vs `99:1413`) is a *variant of one screen* per the audit — and which variant shows is the server's call, not a client comparison of ETA against the clock.
5. **The state→screen map is written the day the contract lands**, as a pure data structure, and is the single place to update when backend states change.

The generic machinery — host route, exhaustive-switch helper, unknown-state fallback, error boundary — is buildable and testable tonight with placeholder states. The real mapping is not.

## 19. Timer / countdown rendering architecture

Section U of the audit confirms the In-service screen shows a remaining-time countdown (sample: "48 mins"), and that the value is dynamic. This area has a specific hazard worth naming.

**The countdown is a *rendering* of server truth, not a client-owned clock.**

| Rule | Why |
|---|---|
| Derive remaining time from **server-provided absolute timestamps** (`endsAt`), never from a client-decremented counter | A decrementing counter drifts, and worse, becomes a second source of truth about whether the session is over. |
| Correct for **clock skew** — compute an offset between device time and server time at session start and apply it | Device clocks are wrong more often than people expect; a user with a skewed clock would otherwise see a wrong countdown. |
| **Recompute on app foreground.** Never trust `setInterval` across backgrounding | JS timers are throttled or suspended in the background; a naive interval will be minutes wrong after a phone-lock. |
| Reaching zero **triggers a refetch, never a state transition** | Session end is a backend decision (§20). The client asking "what now?" is correct; the client deciding "it's over" is not. |
| The Extension flow's new end time comes from the **server response**, not from client arithmetic on the chosen extension | Extension has pricing implications; client-side addition would diverge from billing. |
| One shared ticking source, not a timer per component | Battery and re-render cost. |

`core/time/` — `useServerTime()`, `useCountdown(endsAt)`, skew utilities. **Pure logic, zero design dependency, highly testable — one of the best candidates for tonight.**

## 20. Frontend / backend responsibility boundary

**Backend owns — the client renders the result and never reimplements the rule:**

matching · scheduling · slot generation · availability · ETA computation · cook assignment · reassignment · penalties · refund decisions · booking state transitions.

**Corollaries the audit makes concrete.** Several verified screens *look* like invitations to compute client-side. They are not:

| Screen | Looks like | Actually |
|---|---|---|
| `25:1585` Page 4b taxes popup | A price/tax breakdown to compute | **Display server-computed amounts.** Never compute tax, total or discount client-side. |
| `6:2` Page 12a Cancel policy | A fee schedule (>3 hr → ₹0, 3–1 hr → 25%, <1 hr → 50%) that could be evaluated locally | **Legally consequential.** Render the schedule as content; the *applicable* fee comes from the server. Never evaluate the tier client-side. |
| `104:2336` Page 12c Refund details | "Original Paid − Fee = Refund", trivially computable | **Display all three server-provided values.** Do not compute the subtraction — a client/server mismatch on a refund figure is a trust incident. |
| Instant / Scheduled pickers | Generate available slots | **Render the server's slot list.** No client-side availability logic. |
| In-service countdown | Decide the session has ended | **Refetch at zero.** §19. |
| `99:1413` En route late | Compare ETA to now and decide "late" | **Server tells us it is late.** §18 rule 4. |

**Frontend owns:** rendering, navigation, input capture and *format* validation, optimistic UI for cosmetic actions only, caching and refetch policy, permissions UX, accessibility, error presentation, and the pre-submission booking draft.

**The test:** if a rule has money, legal or fairness consequences, the client displays it and does not evaluate it.

## Summary of proposals

**Stack:** React Native + Expo (managed, CNG) · TypeScript strict · expo-router · TanStack Query · Zustand · expo-secure-store · Jest + RNTL + MSW.

**Dependencies proposed** — install only on approval, `expo install` for all `expo-*`:

| Package | Justification |
|---|---|
| `expo`, `react-native`, `react` | Platform. Versions pinned by SDK. |
| `typescript`, `@types/react` | Language. |
| `expo-router` | Navigation + deep linking for notification→booking routing (§4). |
| `react-native-screens`, `react-native-safe-area-context` | Navigation peers. |
| `@tanstack/react-query` | Server state; the app is predominantly a renderer of server truth (§6). |
| `zustand` | Small client state; booking draft only (§7). |
| `expo-secure-store` | Keychain/Keystore token storage (§9). |
| `expo-constants` | Env access (§10). |
| `react-native-gesture-handler`, `react-native-reanimated` | Sheet/animation peers. |
| `@gorhom/bottom-sheet` | Two confirmed sheets, one requiring a dialog layered above it (§15). |
| `expo-location` | Device permissions/coordinates — vendor-neutral (§16). |
| `expo-notifications` | Lifecycle push (§17). |
| `zod` | Boundary validation once a contract exists; adopted as mechanism, zero schemas now (§5). |
| `jest`, `jest-expo`, `@testing-library/react-native`, `msw` | Test harness (§13). |
| `eslint-config-expo`, `prettier`, `@typescript-eslint/*` | Lint/format. |

**Explicitly deferred:** map SDK, icon library, font packages, crash reporting, E2E runner, `openapi-typescript` — each blocked on a decision that does not exist yet.

**Added by the 2026-08-14 product ruling (R-1):** a **Razorpay checkout dependency** is now committed in principle — `Pay →` opens Razorpay directly and there is no Spoon payment screen. **Not installed tonight:** the integration mode (native SDK vs Standard Checkout in a WebView), key/account, order-creation endpoint and checkout-return contract are backend-contract and engineering decisions that do not exist yet. The client-side rule is already fixed by §18/§20 — after checkout returns, **refetch authoritative booking state; never infer payment success**.

**State ownership:** server state → React Query (authoritative, never mirrored); client state → Zustand (draft + UI only); secrets → SecureStore (isolated module). Booking state is server-owned without exception.

**Navigation model:** expo-router groups — `(auth)` / `(app)` / `(modals)` — with a state-driven `booking/[id]` host. Tab structure unconfirmed and deliberately not committed.

**API architecture:** typed transport + interceptors + single-flight refresh + normalized errors, with a deliberately empty types layer awaiting the contract.

**Testing architecture:** Jest/RNTL/MSW with unit coverage on the whole `core/` layer tonight; component tests written against behaviour so they survive the pending visuals; E2E deferred.
